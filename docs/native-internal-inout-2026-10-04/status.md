# Native internal single-driver inout aliases

Observed missing behavior: parser rejected every `inout`, and hierarchy connections synthesized directional assignments for input/output ports. Treating an inout as either direction would invent a driver or lose the actual driver/read relationship. The existing two-state graph requires one actual driver per bit and cannot represent Z/contention.

The general repair retains undirected per-bit net aliases in the elaborated Design. Hierarchy relocation carries these aliases across independent nested instances; input/output assignment semantics stay intact. Inout actuals must be declared net references/selections/concatenations with matching width, including references to primary inputs. Before graph resolution, deterministic connected components canonicalize driver registrations and reads. Existing single-writer, undriven and combinational-cycle validation therefore operates on the entire alias class. Primary inputs count as real drivers; a second assignment or primary-input driver fails. No multiple-writer Boolean OR or arbitrary driver priority is introduced. Alias origins are retained in the debug database. Designs without aliases avoid allocating component maps.

This supports internal module inouts with one unconditional two-state driver and any number of readers, including driven and read connections spanning multiple hierarchy levels. A driver-only module whose driven port is inout is useful and now accepted; input-only modules remain rejected. Top-level inout stays explicitly Unsupported: no external read/drive/enable/high-impedance contract exists in the current public port model. Four-state/Z, conditional tri-state drivers, bus contention resolution and a true bidirectional Minecraft boundary remain incomplete. This concrete internal support does not complete gap 5 or any broad requirement.
