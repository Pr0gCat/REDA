# A 3D view, with the slice view kept

## Why

The slice view loses the one thing that matters most when a redstone layout is
wrong: **a signal changing layer**. A route climbs a ramp from the gate plane at
y=1 to the track plane at y=3, and in a single-slice view it simply vanishes at
the ramp and reappears somewhere else. Every routing bug this project has hit so
far — the diagonal-descend short, the displaced repeater, the isolation floor —
lives in exactly that cross-layer relationship.

The slice view stays. It is better than 3D at reading exact strengths off a
dense plane, and the eventual floorplan editor needs both: 3D to see the shape,
2D to place things precisely.

## Renderer

three.js, vendored into `viewer/vendor/` and loaded through an import map, so
the page still makes no network request at runtime.

- `three.module.min.js`
- `examples/jsm/controls/OrbitControls.js`

The alternative — hand-written WebGL2 — was considered and rejected. The next
thing after this viewer is a floorplan editor, and an editor needs raycast
picking, transform gizmos and a scene graph. Writing those by hand and then
discarding them when the editor arrives is the expensive path, not the cheap
one.

`seven_segment` has 19,050 non-air blocks. A single `InstancedMesh` handles that
without effort, so nothing clever (greedy meshing, chunking, LOD) is warranted
yet. If a circuit an order of magnitude larger makes it slow, that is the point
to reach for a real technique — not before.

## What the wasm side has to add

`slice(axis, index)` returns one plane. Pulling the whole world plane by plane
every frame would be absurd, so the split is static geometry once, dynamic state
per tick:

```
geometry()  -> Uint8Array   packed, non-air cells only, called once per circuit
strengths() -> Uint8Array   one byte per non-air cell, same order, called per tick
```

`geometry()` packs position and block kind per cell. `strengths()` is the only
thing that changes as the simulation runs, so a tick costs one small array copy
and a buffer update — not a rebuild.

The order must be identical between the two calls, and stated in a doc comment.
A test has to pin it: build `and4`, and assert that for every entry,
`geometry()`'s coordinate and kind and `strengths()`'s value agree with
`World::get` at that coordinate. If the two arrays ever drift out of order the
picture stays plausible and every colour is attached to the wrong block.

## The view

- Orbit camera: drag to rotate, wheel to zoom, right-drag or shift-drag to pan.
  Frame the whole circuit on load.
- Blocks coloured by kind from the existing `legend()`. Dust tinted by strength
  0-15, using the same ramp the slice view uses — the two views disagreeing
  about what a colour means would be worse than having only one.
- **Box clipping**: a min/max range on each of X, Y and Z. This is what makes a
  232 x 5 x 298 sheet navigable, and it is the 3D generalisation of the slice
  view's single index. Clamping Y to a single value must produce exactly what
  the slice view shows.
- Hover picks a block and reports coordinate, kind and strength — the same
  readout the slice view already has.
- Air is not drawn. Neither is any block outside the clip box.

## The two views coexist

A toggle, not a replacement. Both read the same `Session`, so flipping a lever
or stepping updates whichever is visible, and switching between them mid-run
does not reset anything.

## Block shapes and orientation

Drawing every block as a full cube is wrong in two ways that both cost
debugging.

**Redstone dust is not a block tall.** In game it is a flat film on top of the
block below it. Drawn as a full cube, a wire run reads as a solid wall, and the
structure of the routing — which is what one is trying to see — disappears
behind it.

**A repeater, a comparator and a torch are indistinguishable, and so is their
direction.** Direction is not a detail here. Repeaters are one-way, and this
compiler has already shipped a bug where a mandatory repeater landed on a
route's turning corner. A view that cannot show which way a repeater points
cannot show that bug.

Both are fixed by the same move: model the blocks roughly as Minecraft draws
them, and orient them by their `facing`.

| Block | Shape |
|---|---|
| Redstone dust | flat plate, 1/16 high, on the floor of its cell |
| Repeater | low slab, plus **two** small torch nubs — input end and output end |
| Comparator | low slab, plus **three** nubs — two at the front, one at the back |
| Torch | thin post with a head |
| Wall torch | the same, offset against its support block and tilted |
| Lever | small body on the face its `face` property names |
| Slab | half-height box |
| Everything else | full cube |

The nub count alone separates a repeater from a comparator, and the nubs'
placement shows which way it faces — no arrows or overlays needed, and it looks
like what the player will see in game.

**A cell is one unit, and blocks fill it.** A full cube spans its whole cell, so
two adjacent solid blocks are flush with no seam between them. Shrinking cubes
to leave a visible gap makes a wall read as a row of loose beads and, worse,
makes it impossible to tell a continuous run from a broken one — which for
redstone is the difference between a working circuit and a dead one. Where a
shape is smaller than its cell (dust, slabs, repeaters) it is because the block
really is that shape, not for spacing.

This requires `geometry()` to carry each cell's `facing` as well as its kind.
The ordering test extends to cover it: a facing that silently defaults would
point every repeater the same way and look entirely plausible.

## Repeater delay

A repeater's delay is 1 to 4 redstone ticks and it is invisible in the view
today. Minecraft shows it by the gap between the repeater's two torch nubs —
delay 1 has them close together, delay 4 has them at opposite ends — so the
shape work already in place extends to carry it with no new visual language and
no text.

Right now `compile()` hardcodes `delay = 1` on every repeater it places, so this
will render uniformly. That is not a reason to skip it. Minimum delay is the
right default for a latency-minimising compiler, but it is an assumption nobody
has examined, and a view that cannot show delay cannot show it changing when
timing alignment eventually makes delay 2-4 a deliberate tool.

The hover readout reports it as a number, in both the 2D and 3D views.

This needs `geometry()` to carry `delay`. Since instanced geometry is shared,
each delay value needs its own instanced mesh — four at most, and only for
values that actually occur.

## Block edges

Flush blocks solved one problem and created another: a run of solid blocks is
now one undifferentiated grey mass, and you cannot count cells in it or see
where one block ends and the next begins. Coordinates are the unit of every bug
report here, so being unable to count blocks by eye is a real cost.

Every block gets visible edges.

Constraints that shape the technique:

- **No per-block draw call.** `seven_segment` is 19,050 cells and must stay
  interactive while orbiting. Drawing an outline object per instance is not an
  option; whatever is used has to ride along with the existing instanced meshes.
- **Edges must not swallow the view when zoomed out.** At full-circuit framing,
  19,000 outlined cells would read as noise, or worse as a solid dark field.
  Edges should fade out as cells shrink below the size where they are legible,
  and be crisp when zoomed in.
- **No diagonals.** A naive barycentric wireframe draws the triangulation
  diagonal across every quad face. Blocks are boxes; only the box's own twelve
  edges should show.

A fragment shader that derives the distance to the nearest box edge from the
interpolated local position satisfies all three and costs no extra geometry, but
any technique meeting the constraints is fine.

## Later, not now

- Highlighting one net end to end. This is the real debugging weapon and it
  needs net identity exported from the compiler, which today stops at
  `input_positions` / `output_positions`. Worth doing; needs its own plan.
- Anything editable.
- Transparency or depth-peeling to see inside a solid mass. Clipping covers it
  for now.
