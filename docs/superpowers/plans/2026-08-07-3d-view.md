# A 3D view, with the slice view kept

## Why

The slice view loses the one thing that matters most when a redstone layout is
wrong: **a signal changing layer**. A route climbs a ramp from the gate plane at
y=1 to the track plane at y=3, and in a single-slice view it simply vanishes at
the ramp and reappears somewhere else. Every routing bug this project has hit so
far — the diagonal-descend short, the displaced repeater, the isolation floor —
lives in exactly that cross-layer relationship.

The slice view stays. It is better than 3D at reading exact strengths off a
dense plane, and the eventual floorplan editor needs both: 3D to see the shape,
2D to place things precisely.

## Renderer

three.js, vendored into `viewer/vendor/` and loaded through an import map, so
the page still makes no network request at runtime.

- `three.module.min.js`
- `examples/jsm/controls/OrbitControls.js`

The alternative — hand-written WebGL2 — was considered and rejected. The next
thing after this viewer is a floorplan editor, and an editor needs raycast
picking, transform gizmos and a scene graph. Writing those by hand and then
discarding them when the editor arrives is the expensive path, not the cheap
one.

`seven_segment` has 19,050 non-air blocks. A single `InstancedMesh` handles that
without effort, so nothing clever (greedy meshing, chunking, LOD) is warranted
yet. If a circuit an order of magnitude larger makes it slow, that is the point
to reach for a real technique — not before.

## What the wasm side has to add

`slice(axis, index)` returns one plane. Pulling the whole world plane by plane
every frame would be absurd, so the split is static geometry once, dynamic state
per tick:

```
geometry()  -> Uint8Array   packed, non-air cells only, called once per circuit
strengths() -> Uint8Array   one byte per non-air cell, same order, called per tick
```

`geometry()` packs position and block kind per cell. `strengths()` is the only
thing that changes as the simulation runs, so a tick costs one small array copy
and a buffer update — not a rebuild.

The order must be identical between the two calls, and stated in a doc comment.
A test has to pin it: build `and4`, and assert that for every entry,
`geometry()`'s coordinate and kind and `strengths()`'s value agree with
`World::get` at that coordinate. If the two arrays ever drift out of order the
picture stays plausible and every colour is attached to the wrong block.

## The view

- Orbit camera: drag to rotate, wheel to zoom, right-drag or shift-drag to pan.
  Frame the whole circuit on load.
- Blocks coloured by kind from the existing `legend()`. Dust tinted by strength
  0-15, using the same ramp the slice view uses — the two views disagreeing
  about what a colour means would be worse than having only one.
- **Box clipping**: a min/max range on each of X, Y and Z. This is what makes a
  232 x 5 x 298 sheet navigable, and it is the 3D generalisation of the slice
  view's single index. Clamping Y to a single value must produce exactly what
  the slice view shows.
- Hover picks a block and reports coordinate, kind and strength — the same
  readout the slice view already has.
- Air is not drawn. Neither is any block outside the clip box.

## The two views coexist

A toggle, not a replacement. Both read the same `Session`, so flipping a lever
or stepping updates whichever is visible, and switching between them mid-run
does not reset anything.

## Later, not now

- Highlighting one net end to end. This is the real debugging weapon and it
  needs net identity exported from the compiler, which today stops at
  `input_positions` / `output_positions`. Worth doing; needs its own plan.
- Anything editable.
- Transparency or depth-peeling to see inside a solid mass. Clipping covers it
  for now.
